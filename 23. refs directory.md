# ¿Qué es refs?

Dentro de un repositorio Git existe una carpeta oculta:

    .git/

Y dentro de ella hay, entre otras cosas:

    .git/
    ├── objects/
    ├── refs/
    ├── HEAD
    ├── config
    └── ...

El directorio:

    .git/refs/

contiene referencias que apuntan a commits.

- **Idea importante**: Una rama y un tag son referencias que apuntan a commits.

## 1. Dentro de refs

Normalmente hay algo parecido a:

    .git/
    └── refs/
        ├── heads/
        ├── tags/
        └── remotes/

Cada una tiene un propósito.

    refs/heads/

Aquí están las **ramas locales**.

Ejemplo:

    .git/refs/heads/
    ├── main
    ├── feature
    └── develop

Cada archivo contiene el hash del commit al que apunta esa rama.

### Ejemplo

main podría contener:

    a83f91c...

Significa que la rama `main` apunta al commit `a83f91c...`

    A---B---C
            ↑
        feature

El archivo:

    .git/refs/heads/feature

apunta al hash de C.

Si hacemos un nuevo commit:

    A---B---C---D
                ↑
            feature

Git actualiza esa referencia para que ahora apunte a `D`.

## 2. Tags

Los tags están en:

    .git/refs/tags/

Si hicimos:

    git tag v1.0

podríamos tener:

    .git/
    └── refs/
        ├── heads/
        │   ├── main
        │   └── feature
        │
        └── tags/
            └── v1.0

El tag `v1.0` apunta al commit que marcamos.

Por ejemplo:

    A---B---C---D---E
            ↑       ↑
           v1.0    main

Entonces:

    refs/tags/v1.0
            ↓
        commit C

## 3. Remotes

También podemos encontrar:

    .git/refs/remotes/

Aquí Git guarda referencias relacionadas con los repositorios remotos.

Por ejemplo:

    .git/refs/remotes/
    └── origin/
        └── main

Eso representa:

    origin/main

Por ejemplo:

    git fetch origin

actualiza la información que Git tiene sobre las ramas remotas.

## 4. ¿Por qué Git usa la palabra "ref"?

Porque `ref` viene de reference.

Git necesita una forma de decir:

- uiero darle un nombre a este commit para poder encontrarlo fácilmente.

En lugar de que tengamos que recordar:

    a83f91c7d92e...

podemos utilizar:

    main

o:

    v1.0

o:

    feature

Esos nombres son referencias.

## 5. `HEAD`

Podemos pensar en `HEAD` como:

- ¿Dónde estoy actualmente?

Por ejemplo, si estamos en `main`, `HEAD` normalmente apunta a:

    refs/heads/main

Conceptualmente:

    HEAD
    ↓
    refs/heads/main
    ↓
    commit C

Y si hacemos:

    git switch feature

pasa a:

    HEAD
    ↓
    refs/heads/feature
    ↓
    commit D

## Resumen

                    ┌── refs/heads/main
                    │
                    │
                    ├── refs/heads/feature
                    │
                    ├── refs/tags/v1.0
                    │
                    └── refs/remotes/origin/main
                                     
                                      ↓
                                   commits

**Las ramas, los tags y las referencias remotas no son copias de los commits.**

Son nombres/referencias que apuntan a commits.

Son 3 conceptos y todos son referencias.

    .git/refs/

    ├── heads/
    │   ├── main
    │   └── feature
    │
    ├── tags/
    │   ├── v1.0
    │   └── v2.0
    │
    └── remotes/
        └── origin/
            └── main

| Referencia                 | Significado                 |
| -------------------------- | ------------------------- |
| `refs/heads/main`          | rama local `main`         |
| `refs/heads/feature`       | rama local `feature`      |
| `refs/tags/v1.0`           | tag `v1.0`                |
| `refs/remotes/origin/main` | rama remota `origin/main` |

En otras palabras:

- `refs` es el directorio interno de Git donde se almacenan referencias a commits, incluyendo ramas locales (`heads`), tags (`tags`) y referencias de repositorios remotos (`remotes`).
