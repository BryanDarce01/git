# ¿Qué es un tag?

Un tag es una etiqueta que le ponemos a un commit para identificarlo fácilmente.

Imaginemos este historial:

    A---B---C---D---E---F
            ↑

Supongamos que `C` es el commit donde terminamos la versión 1.0 de una aplicación.

Podemos ponerle un tag:

    git tag v1.0

Ahora tenemos:

    A---B---C---D---E---F
            ↑
           v1.0

El tag v1.0 apunta a ese commit.

## ¿Para qué sirve?

Principalmente para marcar versiones importantes:

    v1.0
    v1.1
    v2.0
    v2.1

Por ejemplo:

    v1.0 → primera versión estable
    v1.1 → nueva funcionalidad
    v2.0 → cambio importante

A diferencia de una rama, un tag normalmente representa un punto fijo de la historia.

## Comandos

### 1. `git tag`

    git tag

Muestra todos los tags que tenemos localmente.

Por ejemplo:

    v1.0
    v1.1
    v2.0

### 2. `git tag -l`

    git tag -l

Hace básicamente lo mismo: lista los tags.

La opción `-l` significa list pero de manera explícita.

Por eso:

    git tag

y:

    git tag -l

te sirven para listar los tags.

### 3. Buscar tags

Podemos utilizar un patrón:

    git tag -l "*texto*"

Por ejemplo:

    git tag -l "v1.*"

Podríamos obtener:

    v1.0
    v1.1
    v1.2

O:

    git tag -l "*beta*"

podría mostrar:

    v1.0-beta
    v2.0-beta

Los `*` son comodines.

### 4. `git diff tag1 tag2`

Aquí podemos comparar dos versiones.

Por ejemplo:

    git diff v1.0 v2.0

Git muestra las diferencias entre el estado del proyecto en `v1.0` y el estado en `v2.0`.

Conceptualmente:

    v1.0                         v2.0
    ↓                            ↓
    A---B---C---D---E---F---G---H

Podemos preguntar:

    git diff v1.0 v2.0

- ¿Qué cambió entre la versión 1.0 y la versión 2.0?

### 5. Lightweight tags vs Annotated tags

Aquí está una distinción importante.

#### 5.1 Lightweight tag

Cuando hacemos:

    git tag v1.0

creamos un **lightweight tag**.

Es básicamente:

- Quiero que v1.0 apunte a este commit.

Es una etiqueta simple.

#### 5.2 Annotated tag

Podemos crear:

    git tag -a v1.0 -m "Release version 1.0"

La opción:

    -a

significa annotated.

Este tag contiene información adicional, como:

- nombre del tag

- mensaje

- autor

- fecha

Por ejemplo:

    git tag -a v1.0 -m "Release version 1.0"

Es más apropiado para marcar **releases/versiones oficiales**.

### 6. `git show <tag_name>`

Si tenemos:

    v1.0

podemos hacer:

    git show v1.0

Git muestra información relacionada con ese tag y el commit al que apunta.

Con un annotated tag también podríamos ver la información de la anotación.

Por ejemplo:

    tag v1.0
    Tagger: Pepe
    Date: ...

    Release version 1.0

    commit abc123...
    ...

### 7. Crear un tag en un commit específico

Hasta ahora hemos hecho:

    git tag v1.0

Eso pone el tag en **el commit en el que estás actualmente** (`HEAD`).

Pero podemos decirle a Git:

- Quiero que este tag apunte a ESTE commit.

Por ejemplo:

    A---B---C---D---E
            ↑

Si el hash de `C` es:

    abc123

podemos hacer:

    git tag v1.0 abc123

Entonces:

    A---B---C---D---E
            ↑
        v1.0

### 8. `git tag -f`

Esto es para **mover/reemplazar un tag existente**.

Supongamos:

    A---B---C---D---E
            ↑
        v1.0

Pero nos damos cuenta de que queríamos que `v1.0` apuntara a `E`.

Podemos hacer:

    git tag -f v1.0 <hash-de-E>

La `-f` significa force.

Ahora:

    A---B---C---D---E
                    ↑
                   v1.0

⚠️ Ojo con esto: estamos cambiando a qué commit apunta el tag.

### 9. Eliminar un tag

    git tag -d v1.0

La `-d` significa delete.

Elimina el tag **localmente**.

Importante: esto no significa necesariamente que desaparezca del repositorio remoto.

### 10. Subir tags a GitHub

Aquí aparecen **dos** comandos importantes.

#### 10.1 Subir un tag específico

    git push origin v1.0

Significa:

- Sube el tag v1.0 al remoto origin.

Por ejemplo:

    LOCAL                         GITHUB

    v1.0                          v1.0
    ↓                             ↓
    commit ABC      ─────────→    commit ABC

#### 10.2 Subir todos los tags

    git push --tags

Significa:

- Sube todos mis tags locales que todavía no estén en el remoto.

Por ejemplo:

    LOCAL

    v1.0
    v1.1
    v2.0

Los tres se suben.

## Algo importante: `git push` no necesariamente sube los tags

Esto suele confundir.

Si hacemos:

    git push origin main

estamos subiendo la rama `main`.

Eso no significa que automáticamente estemos subiendo todos tus tags.

Por eso existen:

    git push origin v1.0

o:

    git push --tags

## Resumen

| Comando                    | ¿Qué hace?                                |
| -------------------------- | ----------------------------------------- |
| `git tag`                  | Lista tags                                |
| `git tag -l`               | Lista tags                                |
| `git tag -l "*texto*"`     | Busca/lista tags que coincidan            |
| `git tag v1.0`             | Crea lightweight tag                      |
| `git tag -a v1.0 -m "..."` | Crea annotated tag                        |
| `git show v1.0`            | Muestra información del tag/commit        |
| `git diff v1.0 v2.0`       | Compara dos versiones                     |
| `git tag v1.0 <hash>`      | Crea tag apuntando a un commit específico |
| `git tag -f v1.0 <hash>`   | Mueve/reemplaza un tag                    |
| `git tag -d v1.0`          | Elimina tag local                         |
| `git push origin v1.0`     | Sube ese tag                              |
| `git push --tags`          | Sube todos los tags                       |


### La idea principal

Pensemos en un tag como un n**ombre que le colocamos a un commit importante**:

                    v1.0
                    ↓
    A---B---C---D---E---F---G

Mientras una rama sigue avanzando:

    main
    ↓
    A---B---C---D---E---F---G---H---I

el tag `v1.0` normalmente sigue apuntando al mismo lugar:

    v1.0
    ↓
    E

Por eso los tags son perfectos para decir:

- Este commit representa oficialmente la versión 1.0 de mi proyecto.
